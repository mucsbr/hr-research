# Chrome CDP 接入方案

状态：2026-10-11 已核对现有实现与官方文档，建议作为需要登录来源的主要浏览器模式；尚未实现、连接或部署。用户目前提出方案并要求继续分析，没有提供可从远端访问的 Chrome CDP 地址。

同日用户进一步提出Win/Mac下载式桌面探针，降低非技术人员操作成本并通过终端主动连接解决无法反连。主要接入流程更新为 [桌面探针方案](DESKTOP_PROBE_PLAN.md)；本文件的手工CDP配置作为高级方式。下文的同Chrome采集、资源所有权与质量验证边界仍适用，不再要求普通用户配置调试端口/隧道。

## 结论与范围

采用用户提供、已登录的 Chrome，使用已有 Playwright 的 `connect_over_cdp` 接入。登录和采集都使用这个浏览器的已有默认上下文，不把 Cookie 导出后再交给服务器新起的无头浏览器。无需更换现有任务编排、来源适配、单公司上下文、岗位/舆情归一化、数据库、预算和审计。

官网及公开资讯继续采用既有 HTTP/匿名浏览器路径。BOSS、微博、小红书等需账号的来源优先使用明确绑定的 Chrome。CDP 连接不可用时明确等待连接或人工处理，不静默改用另一浏览器，也不把连接/登录/验证码问题送入付费适配修复。

## 已查明的当前差异

- `browser_sessions.HumanLogin` 启动无头 Chromium，创建新上下文；截图/点击桥始终持有最初的 page，没有跟踪登录弹窗、新标签页或主页面关闭。循环读取标题的异常会进入整场失败和关闭，具体站点触发仍需独立证据。
- `safe_url` 无条件拼接 `scheme://netloc/path`，将真实 `about:blank` 显示为 `about://blank`，这是明确的 URL 显示缺陷；不能据此确定 BOSS 为何转到空白页。
- 招聘 `platform_collectors` 用已保存 storage state 再启动无头 Chromium；舆情 `AuthenticatedBrowserCapture` 同样另起浏览器，并限制资源域、媒体、WebSocket 与 Service Worker。这些设置可能影响站点兼容，不能把小红书错误页直接断定为风控。
- 当前 storage state 保留 Cookie/localStorage/IndexedDB 的部分状态，不代表完整复用浏览器环境。仅将登录改成 CDP、采集仍另起浏览器，不能完成本方案。
- 用户实际微博登录会话记录为 failed，现有错误记录只有通用消息，尚未保存可定位的异常类型/阶段。应补充脱敏诊断，不能把重建会话当修复。

## 拟议数据关系与页面

`浏览器连接 → 平台账号 → 公司招聘来源/舆情来源 → 单公司或单主体任务`。

1. 浏览器连接管理：备注、管理员配置的 HTTP/browser-WebSocket CDP endpoint、连接状态、Chrome 版本、默认上下文、最后连通时间。优先稳定 HTTP 地址，重连时发现当前 browser WebSocket 地址；不能把某个页面的 WebSocket 当作浏览器 endpoint。
2. 账号记录绑定浏览器连接和平台，不推断或编造真实账号身份。同一平台账号可用于多家公司来源；同一个 Chrome profile 中不同平台的登录可复用。需要同平台多个身份时使用不同 profile/Chrome 实例。
3. 操作入口：检查连接、在该 Chrome 打开目标站点、验证可读状态。人直接在 Chrome 登录/扫码/处理验证码；平台不再承担模拟远程桌面登录的主要职责。截图查看可保留为辅助功能。
4. 区分浏览器在线、账号待确认、需要登录、需要人工验证、来源可读。连接成功不等于登录成功；登录成功不等于公司岗位或舆情已采集。
5. 浏览器连接不能自动补齐正式公司在 BOSS 的真实公司页 URL/平台身份；仍使用原来源绑定和归属核对，不能复用已停用的测试来源。

## 采集层改造

- 建立统一浏览器提供器，明确资源是平台自建还是外部借用。CDP 模式取已有默认上下文，创建任务专属标签页；不以 `new_context()` 建立失去登录状态的新会话。
- 招聘通过任务标签页的 DOM 和页面正常请求的响应获取既有适配器所需资料；舆情搜索/详情也走该 Chrome。字段提取、预算、证据、部分覆盖与入库沿用原合同，登录凭据、无关请求和 Cookie 不交给模型/Runner。
- 页面级监听和限制仅作用于任务拥有的页，不能直接沿用 `context.route('**/*')` 等会影响整个用户浏览器的拦截。保留用户原有代理、字体、缓存、Service Worker 和显示设置；不能在借用连接上强行覆盖全局配置。
- 任务结束仅清理任务拥有的标签页、监听和连接。不得执行现有代码中会关闭借用默认上下文的 `context.close()`；断连方式按固定 Playwright 版本验证，不能关闭 Chrome 或用户原有标签页。
- 保留单公司任务与上层批次。一条浏览器连接首版只允许一个采集任务；需对 browser connection 加锁，不能仅依赖每账号锁。不同 Chrome 连接可并发。
- 验证码、403/429、浏览器掉线、来源布局变化分别记录。前几类暂停并保留检查点；解析变化才进入原适配维护流程。不能因 Chrome 掉线自动发送模型请求。

## 部署条件

- 平台和 Worker 仍只在已授权远端运行；不重建本机项目环境。Chrome 可由用户提供，位于用户电脑或常开机器，但必须能从实际 API 容器连接到它。
- 不能把用户电脑的 `127.0.0.1:9222` 直接填给远端容器；必要时通过明确授权的内网或受控隧道连接。CDP 等同于浏览器控制权限，不发布公网无认证端口，只操作明确授权的来源和任务页。
- 如果用调试端口方式，Chrome 136 起默认数据目录不接受 `--remote-debugging-port/pipe`，需要非默认 `--user-data-dir`。可在独立持久 profile 登录一次后长期复用；普通已打开的默认 Chrome 不等于已经提供 CDP。
- 个人电脑关闭/休眠时任务应等待浏览器恢复。若要求无人值守定时采集，Chrome 应放在用户可登录、持续在线的机器上。
- 若后续新增容器网络，继续遵守固定且无重叠的私有172网段；不调整全局 Docker，不改当前业务数据和预算。

## 首版验收

1. 隔离测试中验证 CDP 接入、默认上下文登录复用、任务页创建/关闭、用户原页与 Chrome 未关闭、浏览器重启后重新连接。
2. 验证同浏览器多平台任务串行、不同浏览器并发、掉线后检查点和状态保持。
3. 证明招聘和舆情都走绑定 Chrome；候选程序继续远端 Runner 隔离执行；不得在本机或用户 Chrome 执行 Agent 生成代码。
4. 正式站点验收使用用户明确提供的 Chrome、真实来源和有限页面/记录预算；真实模型请求默认0。BOSS/微博/小红书各自记录实际登录/页面可读结果，不用协议测试代替真实站点质量。
5. 所有写入式夹具仅放独立测试库，不再在正式平台创建 QA 公司或舆情。用户现有账号和任务不重置。
